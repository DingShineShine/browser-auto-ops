# Phase 1 MVP Delivery Plan

## 文件定位

这份文档在软件开发中更接近：

```text
项目一期交付计划
MVP Delivery Plan
Implementation Plan
Milestone Plan
```

它不是完整 PRD，也不是详细技术设计文档。

区别如下：

- PRD：详细描述产品需求、用户、功能、交互、业务规则。
- 技术方案：详细描述架构、模块、接口、数据结构和实现细节。
- 交付计划：描述一期做什么、不做什么、每周做什么、验收标准是什么。

本文件用于向管理层说明一期建设范围、排期和交付边界。

# 单平台报表下载试点一期计划

## 项目背景：自研 browser-auto-ops 底层工具

为了验证 Agent + 指纹浏览器执行企业 RPA 任务的可行性，目前已经先行开发了一套内部浏览器自动化底层工具：

```text
browser-auto-ops
```

它的定位不是业务系统本身，而是给 Agent 提供浏览器操作能力的底层工具，相当于企业内部自研的 browser automation skill / runtime。

当前已验证的能力包括：

- 通过 `chrome-direct` 控制本机真实 Chrome。
- 通过 `ads` 模式对接 AdsPower / ADS 指纹浏览器。
- 通过 `bao daemon` 保持浏览器长驻连接，减少重复授权和重复连接问题。
- 通过 `bao state` 暴露页面可操作元素。
- 通过 `bao click/input/eval` 执行浏览器操作。
- 支持复杂前端组件识别，例如 checkbox、弹窗、确认按钮。
- 支持异步导出任务下载到本地。
- 支持 debug snapshot，用于追踪任务执行卡点。

已经完成的初步验证：

```text
Agent + browser-auto-ops + ADS/Chrome 浏览器
可以完成卖家精灵选品报表导出流程的技术验证。
```

因此，一期项目不是从零直接做完整 RPA 平台，而是在现有 `browser-auto-ops` 技术验证基础上，选择一个代表性平台，把“自动化执行 + 人工介入 + 执行追溯 + 文件落地”做成可试运行的业务闭环。

## 一期目标

选择 1 个代表性店铺渠道，完成从环境搭建、登录、报表下载、人工介入、执行追溯到文件落地的完整闭环。

一期不追求覆盖多个平台，重点验证：

```text
Agent + ADS + browser-auto-ops 是否能稳定完成真实业务流程
```

---

## 一期范围

### 包含

- 1 个店铺渠道
- 3-5 张核心报表
- 1 套 ADS profile
- browser-auto-ops 部署和试运行
- 定时执行
- 人工介入
- 执行追溯
- 下载文件落地
- 失败记录和重跑

### 暂不包含

- 多平台接入
- 多 VPS 调度
- 多 Agent 并发
- 完整任务中心
- 所有报表覆盖
- 复杂权限系统

---

## 建议周期

```text
一期周期：3 周
```

3 周版属于压缩排期，目标是完成单平台 3-5 张核心报表的自动化下载试点，重点验证技术可行性和业务闭环。

若试点平台存在复杂验证码、强风控、报表口径反复调整等情况，可能影响实际交付范围，需要在试运行阶段根据风险做取舍。

---

## 第 1 周：环境搭建与目标平台确认

### 工作内容

- 确认一期试点平台。
- 确认账号、登录方式、验证码方式。
- 配置 ADS profile。
- 安装并验证 browser-auto-ops。
- 验证 `ads` 模式能启动指纹浏览器 profile。
- 验证 `bao state/click/downloads` 等基础能力。
- 验证 Agent 能打开目标平台。
- 梳理 3-5 张优先报表：
  - 下载入口
  - 下载频率
  - 查询条件
  - 文件格式
  - 文件命名规则

### 交付物

- 试点平台确认。
- ADS profile 可用。
- browser-auto-ops 在测试环境安装可用。
- Agent 能打开目标平台。
- 报表需求清单确认。

---

## 第 2 周：核心报表自动下载流程

### 工作内容

- 实现目标平台登录态复用。
- 实现报表页面打开。
- 实现 3-5 张核心报表的筛选条件填写。
- 实现 3-5 张核心报表下载。
- 实现文件保存到指定目录。
- 增加基础异常截图和日志。
- 根据试点页面补充 browser-auto-ops 的可操作元素识别和点击能力。

### 交付物

- 3-5 张核心报表形成自动化下载流程。
- 文件能落地。
- 失败时能看到截图和错误原因。
- browser-auto-ops 能稳定支撑该平台核心下载流程。

---

## 第 3 周：人工介入、执行追溯与试运行

### 工作内容

- 增加任务状态：
  - running
  - success
  - failed
  - manual_required
- 登录失效、验证码、人机验证时进入人工介入。
- 人工处理后可继续执行。
- 记录执行过程：
  - state
  - action
  - screenshot
  - download
  - error
  - summary
- 连续试运行 2-3 天。
- 修复试运行中的稳定性问题。
- 验证下载文件有效性。
- 整理成功率和失败原因。
- 输出一期验收总结。

### 交付物

- 任务可追溯。
- 异常可定位。
- 人工介入流程可用。
- 支持失败重跑。
- 单平台 3-5 张核心报表下载试运行结果。
- 成功率统计。
- 失败原因统计。
- 下载文件样例。
- 二期扩展建议。

---

## 一期验收标准

- 目标平台 3-5 张核心报表可自动下载。
- 文件能保存到指定目录。
- 支持定时执行。
- 登录异常、验证码、风控能进入人工介入。
- 任务失败有截图、state、错误原因。
- 支持任务重跑。
- 连续试运行 2-3 天后，能形成成功率、失败原因和后续优化清单。

---

## 对外说明建议

可以这样表述：

```text
一期建议先收敛到 1 个代表性平台，周期按 3 周评估，优先覆盖 3-5 张核心报表。

先把 Agent + ADS + browser-auto-ops 的单平台报表下载闭环跑稳，包括浏览器控制、报表下载、人工介入、执行追溯和文件落地。

如果一期试运行稳定，再在二期扩展到更多平台和更多报表。这样可以降低一次性接入多个平台带来的不确定性，也能先验证智能 RPA 方案的实际效果和维护成本。
```
